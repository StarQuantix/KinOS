## Context

The repository has no application code or chosen technology stack. OpenSpec 1.10.0 has been initialized for Codex, Kimi Code, Antigravity, and OpenCode. Other tools, including tools without a native OpenSpec adapter, need a shared entry point.

## Goals / Non-Goals

**Goals:**

- Give every contributor the same authority order and change lifecycle.
- Keep the product mission and current boundaries available to every generated OpenSpec artifact.
- Make agent handoffs reviewable without depending on a particular vendor.

**Non-Goals:**

- Select an application architecture, framework, database, hosting provider, or business model.
- Specify the detailed behavior of tasks, recipes, finances, chores, or reminders.
- Introduce elaborate process for trivial, non-behavioral edits.

## Decisions

### Use a short root contract plus generated tool adapters

`AGENTS.md` will contain the stable, human-owned repository rules. Tool-specific skills and commands generated by `openspec init` will provide invocation details. The root contract wins if generated adapters or conversational instructions conflict with it.

Alternative considered: maintain separate full instructions for every agent vendor. This was rejected because those copies would drift and create ambiguous authority.

### Put shared product context in OpenSpec configuration

The project mission, users, opportunity areas, principles, and current maturity will live in `openspec/config.yaml`, which OpenSpec injects into artifact instructions. Accepted behavioral requirements will live only in `openspec/specs/` after changes are archived.

Alternative considered: use a standalone vision or roadmap as the primary product document. This was rejected because it would compete with the requested OpenSpec source of truth.

### Separate durable truth from temporary coordination

OpenSpec artifacts capture durable intent and decisions. Agent assignments, progress notes, and handoff messages remain temporary coordination unless they reveal a requirement or decision, in which case the accountable owner updates the active change.

Alternative considered: commit all agent transcripts and handoffs. This was rejected because volume does not create reliable context and may retain sensitive information.

## Risks / Trade-offs

- [Process becomes heavier than the family project needs] → Exempt truly non-behavioral edits and keep artifacts concise.
- [An agent follows stale generated instructions] → Treat `AGENTS.md` and repository-local OpenSpec artifacts as authoritative; run `openspec update` when tool integrations change.
- [The opportunity list is mistaken for committed scope] → Label it as discovery input and require separate approved changes for product behavior.
- [Sensitive family information enters specs or logs] → Use examples and synthetic data; prohibit secrets and real sensitive records in repository artifacts.
